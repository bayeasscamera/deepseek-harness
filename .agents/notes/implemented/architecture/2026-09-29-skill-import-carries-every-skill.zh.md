# Agent Note: 选中的文件夹会安装它携带的每一个 skill

Status: implemented

[English](2026-09-29-skill-import-carries-every-skill.md) | 中文

## 问题

skill 导入把选择结果当成“一个文件夹里的一个 skill”：它要求选择项必须是目录、要求该目录根下有 `SKILL.md`，并且只返回一个结果。而发现阶段一直接受两种形态——带 `SKILL.md` 的目录，以及直接放在根下的扁平 `*.md` 文件——两者对“什么是 skill”的理解并不一致。操作者按子文件夹分组的任何目录都因此无法导入：选择 `EverythingClaudeCode/`、`anthropics:skills/` 或 skills 根目录本身都会得到 `missing-skill-file`，而扁平 markdown 文件根本无法被选中，因为宿主选择器只提供目录。

## 决策

`settings/importSkills` 现在按发现阶段解析根目录的方式解析选择项。`findSkillSources` 是两侧共用的规则：`skillSourceOf` 决定一个已列出条目如何携带 skill，`discoverRoot` 调用它，因此安装器不会偏离后续扫描所接受的内容。自带 `SKILL.md` 的文件夹就是一个 skill，不再向内下降；其他文件夹会被扫描其中的 skill 目录与扁平 markdown 文件，最多下降到 `SKILL_SOURCE_SCAN_DEPTH` 层，跳过以点开头的条目与符号链接。被选中的 markdown 文件是一个扁平 skill。该动词为发现的每个 skill 返回一个结果，无论安装还是拒绝，因此与真实 skill 并排出现的散文文件会被报告出来，而不是被悄悄安装或悄悄丢弃。

目标始终由清单声明的名称决定，绝不由磁盘上的文件名决定：扁平 skill 安装为 `<skills>/<声明名>.md`，目录型 skill 安装为 `<skills>/<声明名>/`。这使安装后的文件名与 skill 身份是同一个值，也正是扁平场景下冲突得以被观察到的原因。

因此两种形态的冲突检测方式不同，且都是原子的。目录用 `rename` 移动，其在含文件目标上的拒绝即为冲突；扁平文件用 `link` 链接，其在已存在目标上的拒绝即为冲突——`rename` 会悄无声息地替换已安装的文件。两种形态都不先做存在性检查。

深度上限与跳过规则是防止选择项越界的护栏：无界扫描会走遍文件系统，跟随链接则永不终止。没有 `SKILL.md` 且一无所获的文件夹报告 `missing-skill-file`，这与原先单 skill 动词的答复一致，无需新增线上代码。

## 考虑过的替代方案

**保留"一次选中只装一个技能"的读法。** 要求选中的目录根部必须有 `SKILL.md` 是原有行为：操作者按子文件夹整理的那些技能库对导入完全不可见，而发现阶段却能接受它们。现在安装方与发现阶段共用同一套解析规则。

**用选中的文件名寻址目标。** 平铺技能会按文件的当前名字安装，于是用另一个文件名重新导入同一技能会落在第一个旁边而不是与之冲突。清单声明的名称才是身份，安装名随之确定。

**平铺形态也用 `rename`。** `rename` 会静默替换已存在的目标，因此对已安装技能的平铺导入会覆盖它；`link` 才是以拒绝表达冲突的原语。

**先检查目标是否存在。** 先检查再发布是检查与使用之间的竞态，而 `rename`/`link` 已经原子地回答了这个问题。

**无深度上限地扫描选中项并跟随链接。** 宽目录会走遍文件系统，链接成环则永不终止；深度上限与跳过规则把选中项限制在自身之内。

## 后果

`importSkill` 被 `importSkills` 取代，返回 `SkillImportValue[]`。除 settings controller 及其标签页外没有调用方引用旧动词，因此没有 SDK 投影或录制会话随之变动；标签页本就消费多结果报告。

被拒绝的原因词汇未变，调用方区分失败的方式与之前完全一致。调用方现在必须处理的是一个列表：标签页渲染已安装的名称并呈现第一个拒绝原因，这对批量操作是足够的反馈，也只需一条消息而非每个 skill 一条。

发现阶段接受的内容没有变化。`findSkillSources` 读的就是 `discoverRoot` 应用的同一条规则，因此被选中的文件夹安装后，正是发现阶段将从用户 skill 目录列出的那一组。
